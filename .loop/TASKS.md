# TASKS — do them in order, one per loop iteration

Legend: `[ ]` todo · `[x]` done · `[!]` blocked. A `🛑 CHECKPOINT` line means: stop the loop, the human reviews, then ticks it.
Every task's done-definition includes `npm run typecheck && npm test` green plus its own **Verify**.

Where a task lists **Depends:**, do not start it until those ids are `[x]`. Within a parallel lane, still take the first unfinished `[ ]` that this lane owns and whose Depends are met.

## Parallel lanes

After **T01–T03** finish (serial scaffold), work may split into three core lanes that must not touch each other's folders:

| Lane | Tasks | Owns (edit only these) | Progress log |
|---|---|---|---|
| **retrieval** | T04 → T05 → T06 → T07 | `packages/core/src/retrieval/` + colocated `*.test.ts` | `.loop/progress-retrieval.md` |
| **llm** | T08a → T08b → T09b, T10, T11, T13 | `packages/core/src/llm/`, `packages/core/src/steps/` (except coverage orchestration owned by T12b) + tests | `.loop/progress-llm.md` |
| **deterministic** | T09a, T12a, T14, T19a (any order once Depends met) | `packages/core/src/deterministic/` + tests | `.loop/progress-deterministic.md` |

Then **T12b → T15 → T16** are serial (pipeline integration + batch CLI).

Then **api** and **web** lanes run in parallel:

| Lane | Tasks | Owns | Progress log |
|---|---|---|---|
| **api** | T17a → T17b → T18 → T19b → T20 | `apps/api/`, and **must write `docs/API.md` in T17a** before web consumes endpoints | `.loop/progress-api.md` |
| **web** | T21 → T22a → T22b → T23a → T23b → T23c → T24 → T25 | `apps/web/` only; build against `docs/API.md` | `.loop/progress-web.md` |

**Lane rules**
- Lane agents must **NOT** edit `.loop/TASKS.md` (the orchestrator / plan-review does). Marking `[x]` and choosing the next task is the human or the single-agent loop in `.loop/PROMPT.md` when not parallelised.
- Lane agents append to their lane log file above — **not** to `.loop/PROGRESS.md` unless running the single-agent PROMPT loop.
- Do not edit another lane's folders. **Known collision avoided by splits:** T09a/T12a/T14/T19a own `deterministic/`; T09b/T10/T11/T13 own `steps/` + `llm/`; T12b may add `steps/coverageLoop.ts` (or equivalent) only; T19b owns `apps/api` regenerate/edit routes only (calls `@prep/core` merge).
- T26–T30 and checkpoints stay serial after the lanes above (or after web/api as noted per task).

## Phase 1 — Retrieval (no LLM)
- [ ] **T04 safeFetch.** **Depends:** T01–T03. **Lane:** retrieval. Returns `{ok:true,...}|{ok:false,url,reason,status?}` — never throws for remote failures. **Verify:** tests against a local node:http server: 404, timeout, oversize, wrong content-type, redirect to 127.0.0.1 blocked in production mode, robots disallow.
- [ ] **T05 cleanPage.** **Depends:** T04. **Lane:** retrieval. cheerio: extract title, meta description, links (anchor text + absolute URL via `new URL(href, pageUrl)`, BEFORE stripping nav/footer), main text (prefer main/article, strip script/style/nav/footer/forms), collapse whitespace, cap ~12k chars. **Verify:** tests on fixture HTML.
- [ ] **T06 crawl + rankLinks.** **Depends:** T05. **Lane:** retrieval. Deterministic scorer on anchor text + path + (after fetch) page text: hiring signals (careers, jobs, hiring, interview, recruit, join, handbook, process, "how we hire", take-home, onsite), about signals (about, company, mission, team, values, culture, what we do), penalties (login, privacy, terms, cookie, pricing, legal, assets, fragments, mailto). Classify pages hiring/about/other with a content-score threshold. Output `ResearchBundle { homepage, aboutPages, hiringPages, otherPages, skipped[], unreachable:boolean }`. Follow relative links; do not assume public hostnames (local fixture hosts OK when allowed). **Verify:** acme → finds the buried hiring page; quietco → zero hiring pages, no throw; unreachable → `unreachable:true`; no hard-coded paths (grep).
- [ ] **T07 searchDiscussion.** **Depends:** T06. **Lane:** retrieval. Company name from homepage title / og:site_name / domain. ## Phase 2 — LLM layer
- [ ] **T08a LLM providers + limiter.** **Depends:** T02. **Lane:** llm. Provider interface with Gemini (REST, JSON response mode) and Groq (OpenAI-compatible REST) via native fetch. Token-per-minute + request-per-minute sliding-window limiter (estimate tokens = chars/4), shared process-wide. Retry 429/5xx/network with exponential backoff + jitter, honour Retry-After / retry-delay hints, max ~6 tries, then fall back to the other provider if configured. **Verify:** fake provider tests: 429→429→ok; limiter delays when budget exceeded; fallback when primary always-fails.
- [ ] **T08b generateJson + wrapUntrusted + cache.** **Depends:** T08a. **Lane:** llm. `generateJson({system, parts, schema, label})`: parse → zod → on failure 1 repair call including the zod errors → typed `LlmError`. `wrapUntrusted(source, text)` wraps in `<untrusted_document source="...">…</untrusted_document>` and neutralises any closing tag inside text (§11: JD + fetched pages are data, never instructions). Optional disk cache keyed by sha256(provider+model+prompt) when LLM_CACHE_DIR set (dev only). **Verify:** invalid JSON→repaired; always-fail→LlmError; wrapUntrusted neutralises embedded closing tags.

## Phase 3 — Pipeline steps
- [ ] **T09a groundRequirements (deterministic).** **Depends:** T02, T03. **Lane:** deterministic. Pure functions in `deterministic/`: (1) `groundRequirements` — drop items whose `evidence` isn't found in the JD (normalised, case-insensitive; token-overlap ≥ 0.8 fallback); (2) priority override from cues in the evidence line or its section heading: nice ← nice to have / bonus / preferred / a plus / ideally / familiarity with; must ← required / must / requirements / you have / you will need / minimum; (3) dedupe; (4) ids `r1..rn` in JD order. Thin JD (few chars or < 3 grounded reqs) ⇒ `notes.thin_jd=true` + explanation. **Never invent requirements** (§10): thin JD ⇒ thin output. **Verify:** tests — the rich fixture JD matches `fixtures/expected` must/nice; injected "Knows COBOL" and a fabricated requirement are dropped; 2-line JD yields ≤ what it literally says.
- [ ] **T09b extractRequirements (LLM step).** **Depends:** T08b, T09a. **Lane:** llm. LLM returns `{title, seniority, location, company?, responsibilities[], requirements:[{text, kind, priority, evidence, section}]}`. JD text sent **only** via `wrapUntrusted('jd', jd)`. Then call T09a post-processing. **Verify:** fake-provider tests assert wrapUntrusted used; grounded output matches T09a expectations when model returns fixture-like JSON.
- [ ] **T10 buildBrief + extractInterviewProcess.** **Depends:** T08b. **Lane:** llm. Brief from homepage/about pages only; page text via `wrapUntrusted`; `sources` filtered by code to fetched URLs; if nothing usable ⇒ honest summary stating what was and wasn't found (unknown company ⇒ no fabrication, §10). Interview process from hiring pages + discussion: `interview_process: { found:boolean, stages:[{name, type: take-home|system-design|pair-programming|technical-screen|behavioural|onsite|other}], sources[] }` (extension field). **Verify:** acme → take-home + system-design found; quietco → `found:false`, honest brief; evil page's injection has no effect.
- [ ] **T11 generateQuestions per category.** **Depends:** T08b. **Lane:** llm. Four separate functions + prompts: `technical` (technical+domain reqs, stage-aware: take-home debrief questions if take-home found), `behavioural` (behavioural reqs, STAR outlines), `system-design` (only if a system-design stage was found OR seniority ≥ senior OR reqs mention architecture/scale — decided in code), `company-fit` (brief + values + process). Each call receives only its requirements (with ids). Untrusted context via `wrapUntrusted`. Code: drop requirement_ids not in the input set, clamp difficulty, assign `q` ids, `meta.origin='generated'`. **Verify:** fake-provider tests assert the four calls are separate with different instructions; acme vs quietco produce different category sets.
- [ ] **T12a findGaps (deterministic).** **Depends:** T02. **Lane:** deterministic. `findGaps(requirements, questions)` → uncovered ids, must-first (must gaps before nice). Pure; no LLM. **Verify:** unit tests — covered req absent from list; must ordering; empty questions ⇒ all req ids.
- [ ] **T12b Coverage loop (second pass).** **Depends:** T11, T12a. **Lane:** serial after llm+deterministic pieces (orchestrator / single loop). Loop: pass 1 = draft; while must-gaps && passes < 3 → `generateQuestions` for just the gap requirements, routed to the category by `kind`; recompute via `findGaps`. After the cap, a deterministic fallback question per remaining must-gap (`meta.origin='fallback'`) so no must ships uncovered (§4); nice gaps may remain and are listed. Record `coverage.passes` and per-pass log in `research_log`. **Verify:** tests — gap closed on pass 2; stubborn gap → fallback at pass 3; passes count correct; nice-only gaps don't loop.
- [ ] **T13 generateFlashcards.** **Depends:** T08b, T11. **Lane:** llm. From questions + requirements; code guarantees ≥1 card per must requirement (deterministic fallback card), ids `f1..`. **Verify:** tests.
- [ ] **T14 allocateSchedule (deterministic).** **Depends:** T02. **Lane:** deterministic. Score each question: priority weight (must=2, nice=1, max over its reqs) × 10 + difficulty × 3 + (covers a must with only one question ? 5 : 0). Minutes per question by difficulty (1→10, 2→20, 3→30). Sort desc. Days = N exactly (§8). Learning phase = first ceil(N×0.7) days (min 1), then review/mock days. Greedy fill learning days front-loaded (earlier days get the high scorers; balance by minutes). Review days revisit the hardest/must questions (spaced), last day = "Mock interview + weak spots". If N > questions, extra days become spaced review of earlier material — never an empty day. Focus label = dominant category/requirement of the day. All minutes integers. Cap per-day minutes (e.g. 180) and note overflow. Every must-have requirement appears somewhere in the schedule's questions. **Verify:** tests for N=1, 2, 5, 14, 60, 0 questions; every must requirement appears; ids exist; day-1 mean score ≥ last learning day mean; integers only.
- [ ] **T15 runPipeline.** **Depends:** T06, T07, T09b, T10, T11, T12b, T13, T14. Orchestrates: validate input → extract (no retrieval for JD, §3) → crawl → search discussion → brief + process → questions per category → coverage loop → flashcards → schedule → assemble `source` (jd_chars, researched_at, pages_used) → `validateKit`. Emits progress events `{step, status: running|done|skipped|failed, detail}`. Unreachable site ⇒ still `ok` kit from the JD with an honest brief + `research_log.company_unreachable=true` (FAQ: missing hiring page / partial research ≠ `failed`). Throws `PipelineError(code)` only if no kit is possible (empty JD, LLM unavailable after retries+fallback). Skipped sources recorded in `research_log.skipped`, never abort the run (§2). **Verify:** integration test with fake LLM over all fixtures; assert `failed` only when no kit.
- [ ] **T16 Batch CLI.** **Depends:** T15. Parse `--input/--output` (node:util parseArgs) for exact `npm run evaluate -- --input <cases.json> --output <kits.json>` (§9). Allow private hosts. Run cases with concurrency 2 sharing the one limiter; per-case timeout ~4 min; one failing case never stops the run; write Appendix B (one entry per input case id, any order; write after each case so partial results survive a crash). Uses each case's `days`. Same `runPipeline` as the API. Print a summary table + elapsed time. Exit 0 if the run completed. **Verify:** with `npm run fixtures` running + a real free-tier key: `npm run evaluate -- --input fixtures/cases.json --output out/kits.json` completes < 15 min, output validates against the Appendix B schema (add `scripts/check-output.ts`).
- [ ] 🛑 **CHECKPOINT B** — human: read out/kits.json for each case. Are requirements faithful? Is the stub honest? Is the quietco brief honest? Did the injection fail? Fix prompts before building UI.
